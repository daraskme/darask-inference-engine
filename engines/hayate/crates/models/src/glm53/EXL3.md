# EXL3(turboderp GLM-5.3-Flash-exl3 sc_2.60bpw)を Hayate で動かす(phase29/glm53x3)

基点は main 7e11d77。下調べは `/mnt/NVME4TB/hayate/spill/maya-bench/exl3-import-plan.md`。
ユーザーの決定(10/20): EXL3-SC 2.60 を組み込み、serve の既定を f100 から置き換える方向で進める。LoRA と Studio の連携は保つ。

## 1. 設計

### 重みの持ち方

| 部分 | EXL3 チェックポイント | Hayate の HYT(`glm53x3-sc260`) |
| --- | --- | --- |
| routed エキスパート(層 3〜44) | トレリス 2.5 bpw(層 3 だけ 3.5)、suh/svh FP16 | **そのまま**。新しい QuantSpec `Exl3 { k2, cb }`(タグ 7) |
| 注意、共有エキスパート、密層 0〜2、lm_head | トレリス 6 bpw | 変換時に CPU で復号し、f100 と同じ per-tensor FP8 E4M3 で書く |
| KDA の q/k/v | 1 本の `qkv_proj`(6 bpw)と `conv1d` | 復号して q/k/v、q/k/v_conv1d に分ける(f100 と同じ名前) |
| ルーター、b/f/g_a/g_b、索引の wk / weights_proj / kv_b など | FP16 のまま | f100 と同じ型(BF16 か FP8)。BF16 由来の FP16 は BF16 へ無損失で戻るか検査する |
| 埋め込み、norm、hc_* | BF16 / F32 | そのまま |
| MTP(層 45)、vision | 4 / 6 bpw | 使わない(f100 にも無い) |

- 非エキスパート部を EXL3 のまま動かすと、注意・KDA・MLA・索引の融合カーネルを全部作り直すことになる。
  変換時に復号して FP8 にすれば、ランタイムの dense 経路は無変更で済む。
- 代わりに量子化を 2 回重ねる。第 6 段階の FP8 化は KLD +0.0045 だったので、上乗せは +0.005 前後の見込み。

### 行列の画像(タグ 7)

- HYT の形は今までどおり `[出力, 入力]`(gate/up は [2048, 4096]、down は [4096, 2048])。
- 中身は EXL3 の並びのまま:
  - `trellis`: [入力/16][出力/16] のタイル。1 タイル 16·k2 バイト(k2 = 2K。2.5 bpw なら 5)
  - `suh`: FP16 [入力]
  - `svh`: FP16 [出力]
  - 各区間を 256 B 境界に揃える。
- `ExpertFormat` の 4 バイトは format=3、grid=k2、group=cb(mul1 = 2)、reserved=0。エキスパート 1 個の画像は gate | up | down。
- 1 エキスパートの大きさ: 2.5 bpw で 7,901,184 B、3.5 bpw で 11,046,912 B。
  可変サイズのスロット(第 22 段階)にそのまま乗る。

### 層の種類

層ごとに次のどれか 1 つ。EXL3 と LOWBIT がエキスパート単位で混ざった層は、ロード時に拒否する。

- 一様(NVFP4 / FP8)
- LOWBIT 混在
- EXL3

### カーネル(Project Maya PR #265 と exllamav3 の EXL3 実装を移植。どちらも MIT)

- **decode**: `hayate_glm_exl3_gate_up` / `hayate_glm_exl3_down`。
  - 引数は LOWBIT 版と同じ(画像の表、形式の表、共有エキスパートの FP8、M 1〜4)。
  - 1 ブロックが出力 128 個を受け持ち、入力の回転(x·suh、128 点 Hadamard)を共有メモリで行い、タイルを mma.m16n8k16 の断片に直接復号する。
  - 共有エキスパートは同じ起動の 9 番目の組として、今の FP8 の行カーネルで計算する。
  - 出力は今と同じ `decode.product`(SwiGLU の積、Hayate と同じクリップ)と `decode.expert` に書く。
  - なので LoRA の側路(`lora_experts`)、ルーター、CUDA graph は変えない。
- **prefill**: `hayate_glm_grouped_exl3_gate_up` / `_down`。
  - packed の grouped GEMM と同じ引数にする。
  - 128 入力ずつ、行を suh で回転して FP16 で共有メモリに置き、タイルを B 断片に復号して f16 の mma に通す。最後に 128 出力ずつ H と svh をかける。
  - gather、scatter、`lora_grouped` は今のまま使う。
  - 1 トークンの旧経路のために、BF16 への復元カーネル(`exl3_restore`)も作る。これは試験の基準にもする。
- **CPU**: Maya の AVX2 版を Rust に移植して、`Format::Exl3 { k2 }` の区間カーネルにする。
  - 入力の回転はミスごとに 1 回。出力 128 個を 1 単位にして、スレッドに分ける。
  - LoRA(`HostExperts::apply`)は今のまま使う。

### Studio との連携

- serve の `glm53` のまま、`glm_hyt` の既定を新しいディレクトリに切り替えるだけにする。
- エキスパートの GPU/RAM の階層、弾力的な縮小(7e11d77)、セッションの KV 保存、OpenAI 形式の API は、画像の中身に依らないので変えない。
- 切り替えは、他のセッションに確認してから行う。

## 2. 試験と測定の順序

GPU を使う手順は、毎回ユーザーと他のセッションに確認したうえで、`gpu_slot --timeout 30` の下で走らせる。

1. CPU:
   - Python の参照デコーダを、Maya の `data/exl3-exllamav3`(exllamav3 自身の fixture)とビット一致させる。
   - 変換器で HYT を作る。
   - Rust の CPU カーネルを、参照とビット一致(またはほぼ一致)させる。
2. GPU(要確認):
   - カーネルの試験(CPU の参照と照合)。
   - 448 行の KLD / top-1 / NLL を、`fp8-ref` と `glm53_eval compare` で測る。
   - 速度は `spill/glm53d/b` の短文・code1k・long32 で測る。
3. GPU(要確認): 拒否の具合を、LoRA の有無で比べる。EXL3 は Z.ai 原版(検閲あり)の重み。
4. serve の既定の切り替え(他のセッションに確認してから)。

## 3. 進み具合(10/20 12:30、GPU 未使用)

### CPU で確かめたこと
- Python の復号(`hayate_tools.glm53_exl3`)は、exllamav3 自身の fixture 13 種類(K 1〜8、1.5 / 2.5 / 3.5、コードブック 3 種)と、状態も W' もビット一致した。Rust 版も同じ fixture で一致した。
- 復号した重みを dealignai FP8 と比べた結果:

  | 部分 | cos | 相対誤差 |
  | --- | ---: | ---: |
  | 6 bpw の行列 | 0.9998 | 2.0% |
  | 2.5 bpw のエキスパート | 0.978〜0.982 | 19〜21% |
  | 3.5 bpw のエキスパート | 0.994 | 11% |
  | FP16 の生テンソル、conv の分割 | 1.0 | 0 |

- 変換した HYT の非エキスパート部は、f100 と同じ名前・形式・形になった。FP8 にした dense は f100 との差が 3〜4%(6 bpw の誤差と FP8 の丸め)。ルーター、hc_*、埋め込みは f100 とビット一致し、BF16 への変換もすべて無損失だった。
- CPU エキスパート(AVX2、K2.5、M=1):
  - 1 コアで 2.78 ms。
  - P コア 8 本のプールで 0.55〜0.59 ms(変換 6 プロセスと同時に走らせた値)。
  - n2 g32 の 0.189 ms のおよそ 2〜3 倍。
- プール経由の EXL3 区間は、直接の計算とビット一致した。`forward_layer_formats` も、復号済みの重みを使った F64 計算と一致した。
- 既存の CPU 試験はすべて通過: core 40、kernels 44(ignore 2)、models 191(ignore 24)、Python 37。
- clippy で私の変更による指摘はない。残っているのは main にもともとある `executor.rs` の clone、`h3_hires`、`moss`、`expert_cache` の警告だけ。

## 6. VRAM にないエキスパートを PCIe で運ぶ経路(device decode)

ユーザーの決定: 「VRAM にないエキスパートを PCIe で運ぶ経路を作って速度を取り戻す」。目標は f100 並みの decode(short 61.5、code1k 46.1、long32 40.1 tok/s)で、品質は変えない。

### 運び方: ゼロコピーではなくコピー用カーネル
- 最初の案はゼロコピーだった。pinned の RAM 画像を、GPU の decode カーネルが UVA 越しに直接読む。
  - 測ると遅かった(1 エキスパート 1.66 ms、4.7 GB/s)。読む側のブロックが少なく、PCIe の待ちを埋められない。
- そこで、画像を VRAM の一時スロットに写すカーネル(`hayate_glm_exl3_fetch` と `hayate_glm_dev_prefetch`)を使う。
  - 7.9 MB で 25〜32 GB/s。DMA は 32〜36 GB/s。
  - 写し元はルーターが GPU 上で決めるので、DMA は使えない(CUDA graph の memcpy ノードは、アドレスを捕獲時に固定する)。
- 1 スロットあたり 4〜8 ブロックでも 188 ブロックと同じ帯域が出る(`glm53_exl3_gpu_fetch`)。

### 直列レーン(v1、08d66eb)
- ルーター(`device.cu` の `route`)が層ごとに振り分ける:
  - 選んだ 8 個のうち、VRAM に無く RAM に画像があるものを n 個とする。最初の `take[n]` 個は CPU に回す。
  - 残り(最大 4 個)は、ホストの画像をスロットに写してから、層のエキスパートカーネルが GPU で計算する。
  - CPU にはメールボックスの bit 31 で、レーン分を外して渡す。
- LoRA の側路は画像があるエキスパートに GPU で掛かるので、レーン分にも同じ式が掛かる。
- `--pcie-take` で表を変えられる(既定 0,0,1,1,2,2,3,3,4)。
- 結果: short 46.5、code1k 40.2、long32 33.0 tok/s。
  - レーンなしは 45.7 / 40.6 / 31.6 で、ほとんど変わらない。
  - 写す時間(トークンあたり 3.4 ms)が、そのまま GPU の待ちになる。

### 重ねる試み(v2、不採用)
- 写す処理を別ストリームに分けて、VRAM 上のエキスパートの計算と重ねた。レーン分は合流のあとに、2 回目として計算する。
- 速くならなかった(45.9 / 40.5 / 32.1)。
  - 1 層の計算は SM 1 波(約 0.14 ms)で終わる。2 回に分けると 2 回目もまるまる 1 波かかり、重ねて得た分を打ち消した。

### 先読み(v6、採用)
- 層 k のルーターの直後に、層 k の ffn_norm 出力へ層 k+1 のゲートを掛けて上位 8 個を予測する(`predict`)。
  - そのうち VRAM に無く RAM にあるものを、スコア順に `--pcie-prefetch` 個(既定 1)まで選ぶ。
- 選んだものは別ストリームのコピー(`prefetch`、1 スロット 8 ブロック)が、層の偶奇で分けた 2 組のスロットへ写す。
  - 写す時間は、層 k のエキスパート計算と層 k+1 の注意機構の陰に入る。
- 誰もコピーを待たない。合流はトークンの最後の 1 回だけ。
  - コピーは、スロットが全部写ったときに印 `seq << 8 | layer` を付ける。
  - 層 k+1 のルーターは、印が合ったスロットだけを使う。
  - ルーターは最初に自分の印を `progress` に書く。その層あてのまだ始まっていないコピーは、それを見て打ち切る。
  - 間に合わなかったミスは、直列レーンか CPU に回る。
- 誤りに気づいた点:
  1. 各層でコピーを待つ合流を入れると遅くなった(short 39.8〜44.1)。
  2. 待たない方式でも、コピーを 188 ブロックで走らせると遅かった(39.7〜43.0)。コピーのブロックが SM に居座り、エキスパートや注意機構のカーネルが入れない。8 ブロックに絞って解決した。
  3. 先読み数 2 以上では、多くが間に合わない(使えたのは 17% 前後)。そのうえ外れた分が帯域を食う。1 が最良。
- 予測の当たり: 先読みしたものの 63〜71% を実際に使う。
- `glm_pcie` の行(prefetched / prefetch_used / lane_serial / ram_misses_cpu)で数えられる。

### 品質(448 行、§4 と同じ条件)

| 構成 | KLD | max KLD | top-1 |
| --- | ---: | ---: | ---: |
| レーンなし | 0.0784 | 0.705 | 88.4% |
| v1(先読みなし) | 0.0822 | 0.724 | 88.6% |
| 先読みなし、レーン最大(take 0,0,0,0,0,1,2,3,4) | 0.0803 | 0.754 | 88.8% |
| v6 先読み 1(4 回) | 0.0807〜0.0840 | 0.672〜0.753(1 回だけ 1.158) | 87.7〜88.6% |

- どのエキスパートを CPU(F32)で計算し、どれを GPU(FP16)で計算するかで、数値がわずかに変わる。
- 先読みはコピーが間に合うかどうかで行き先が変わるので、実行ごとに結果がわずかに揺れる(非決定的)。
- GPU に回す量を最大にしても KLD は上がらない(0.0803)。なので、この揺れは計算誤差の差で、品質の劣化ではない。品質の基準も通過。
