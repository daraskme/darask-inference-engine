# 第21段階: serve の速度のボトルネック探し(phase21/glm53x)

基点は main 7522ab6(第19・20段階の統合)。計測は `spill/glm53d/b`(`one.sh` / `driver.sh` / `serve_budget.sh`)。
serve の既定重みは `glm53q-q4-gptq`(エキスパート NVFP4 GPTQ + 第6段階の dense FP8)。

## 1. 時間の内訳(短いプロンプト、GPU hit 0.82、1 トークン約 35 ms)

| 項目 | ms | 備考 |
|---|---:|---|
| CPU のミス計算の待ち | 22〜24 | 1 トークン約 0.84 GB(ミス 59 個)、DRAM 律速 35〜40 GB/s |
| GPU 経路 | 12〜13 | attention 7.7、FFN mHC + router 1.4、GPU エキスパート 3.9、head 0.4 |
| graph の外(準備・回収・保守) | 1.7 | 保守(1 スワップ/トークン、同期)が 1.3〜1.7 |

- 1 トークンの GPU 経路が読む重みは約 8 GB(attention・dense・shared・hit したエキスパート)。1.5 TB/s なら約 5.3 ms なので
  帯域の下限に対して約 64%。残り約 4 ms は小さい kernel の隙間と mHC/KDA の依存(Astra の見積もりでも 0.5〜1.5 ms 程度しか
  取れない)。広い融合は手間の割に 3% 程度。
- 1% の hit 率 = 約 3.4 エキスパート = 約 48 MB = CPU 約 1.2 ms。エキスパート数(slot)を +10% 増やすと hit は
  +3.5 ポイント前後、約 4 ms。これが一番大きいてこ。

## 2. 試したこと・分かったこと

- **device 経路の CPU 帯域が sync 経路より低く見える件**(32 対 40 GB/s): 7,531 個のミスで cpu_ms 3,038 に対し
  worker_ms 2,883、dispatch_ms 2,984 なので、ジョブあたりの固定費は 29 µs(層 42 個で約 1.2 ms)。主因は 1 層あたり 1〜2 個の
  小さなジョブ(1 個 14 MB = 0.34 ms)で 8 スレッドの先頭と末尾の効率が落ちること。device 経路の問題ではない。
- **保守(decode 中の 1 スワップ/トークン)**: 第20段階の probe のあとは、コード生成では得より損。リプレイ(コスト 1.8 ms/スワップ):
  ヒステリシス 4 → agent +2.7 / code1k −1.2 / code8k −1.5 / long32 −1.0 / short −0.15 ms/トークン、
  ヒステリシス 16 → +1.96 / +0.05 / −0.01 / −0.02 / +0.20。**既定を 4 → 16 にした。**
- **defer-below 0.10**: 24.7 tok/s(基準 25.6)で速くならない。skip-cpu-below 0.20 は eval で −21% の時間・KLD +0.005 だが、
  品質の予算(量子化に使う)と取り合いになるので既定オフのまま。
- **短いプロンプト(32 トークン未満)でも probe を始める**ようにした(以前は CPU の step 経路で戻って配置が一度も動かなかった。
  GPTQ 重みの短い英文で hit 0.745 → 目標 0.81)。
- **150 GB の 3+4 bit 混合案**(`plans/pass3/b150.json`、NVFP4 コンテナに展開した版): Rust の固定コーパス
  KLD 0.0524 / top-1 90.62%(max KLD 0.693)。GPTQ(KLD 0.0380 / 89.96%)に対して KLD +0.014。目標(KLD 0.05 前後、
  top-1 88% 前後)内。速度はコンテナが NVFP4 のままなので 27.4 tok/s(hit 0.811)でバイト削減の効果はまだ出ない。
  Python の見積もりは 0.0476 で、Rust の方が 0.005 高い。
- **LOWBIT の GPU kernel**(Sol): 正しさは通過(参照、MoE、NVFP4 とのビット一致、変換)。M=1 の 8 エキスパート:
  NVFP4 gate/up 65.8 µs・down 37.1 µs、nf3 g32 70.7・41.9 µs、n2 g32 55.7・36.3 µs。読むバイトが 77% / 59% でも
  時間は NVFP4 より長い/やや短いだけ(0.75〜1.15 TB/s、復号の計算が律速)。全部 3 bit のヒットでも 1 トークン +0.4 ms 程度で、
  GPU 側の LOWBIT の目的は速度でなく同じ VRAM に載る数を増やすこと。
- **LOWBIT の CPU kernel**(Sol): NVFP4 42.8 GB/s(以前 39.7、ビット一致)、LOWBIT 10 形式 37.5〜42 GB/s で参照とビット一致。
  1 エキスパート nf3 g32 244 µs、n2 g32 189 µs(NVFP4 331 µs)。GPU 順序版(CPU を GPU とビット一致にする)は 24 GB/s で遅いので既定オフ。

## 3. serve の VRAM 予算

serve は `Options::vram_budget` を 84 GiB 上限で作っていた(空き − 7 GiB)。prefill の作業領域 8.3 GB はエキスパートの外に
予約され、decode 中は空いたままになる(15 GB 空き)。エージェントループ(34K + 約 2.2K/ターン、32 トークン返答)で比べた:

| 上限 | GPU エキスパート | prefill ピーク時の空き | decode(ターン 2〜4) | 最初の 34K prefill | 追記 prefill(2.2K) |
|---|---:|---:|---|---:|---:|
| 84 GiB | 4,771 | 7.5 GiB | 12.6 / 16.0 / 15.4 | 31.6 s | 5.0 / 5.0 / 5.1 s |
| 90 GiB | 5,226 | 3.0 GiB | 16.5 / 17.1 / 17.9 | 40.2 s | 5.8 / 4.5 / 3.9 s |
| 92 GiB | 約 5,370 | 約 3 GiB | 18.7 / 18.4 / 18.1 | 52.7 s | 5.0 / 3.8 / 4.4 s |

- prefill は空き VRAM に合わせて作業領域を決める(チャンクを小さくし、それでも足りなければキャッシュを借りる)ので、
  上限を上げてもピークは同じ約 94.7 GB(OOM の危険は増えない)。代わりに最初の大きな prefill のチャンクが小さくなり、
  エキスパートの H2D 回数が増えて遅くなる。追記 prefill(数 K トークン)は影響なし。
- 1 GiB で約 76 エキスパート。ただし 32 トークン返答 4 ターンの上の表は誤差が大きかった(±10%)。同じバイナリ(第21段階)で
  返答 128 トークンに揃えて 84 GiB と自動(90 GiB)を比べると:

| 上限 | GPU エキスパート | decode(ターン 1〜4) | 最初の 34K prefill | 追記 prefill(2.2K)の TTFT |
|---|---:|---|---:|---|
| 84 GiB | 4,771 | 13.9 / 17.3 / 16.8 / 16.6 | 30.7 s | 5.5 / 5.6 / 5.5 s |
| 90 GiB(自動) | 5,199 | 15.2 / 18.3 / 18.0 / 16.9 | 38.6 s | 5.2 / 5.1 / 5.1 s |

  ターン 2〜4 の平均は 16.9 → 17.7 tok/s(+5%、誤差の範囲)、最初の大きな prefill は +8 s(+26%)。元が取れる返答長は
  約 3,000 トークンなので、**上限は 84 GiB のまま**にした(余白だけ 7 → 2 GiB: 空きが少ないときに予算を使い切れる)。
- 上限を上げる価値を出すには、最初の大きな prefill の前に一時的にキャッシュを縮め(`resize`)、終わったら戻す方式が要る
  (8 GB の往復で 2〜3 秒、遅れ 8〜20 秒に対して)。未実装。

## 4. 残り(効果の大きい順)

1. **LOWBIT をランタイムに組み込む**(形式別 slot、デバイスのルーティング、CPU への形式の受け渡し、prefill の変換、RAM コピー付きキャッシュ)。
   150 GB 案で CPU のバイトが 0.63 倍(約 −8 ms/トークン)、RAM に余裕ができるので入れ替えの D2H も不要になる。
2. **MTP をデバイス経路で**(CPU の読み出しが支配的な間は、検証のエキスパート集合が膨らむ分を回収できるか要計測)。
3. prefill の作業領域の縮小(スコア行列を query 方向に分割、バッファの寿命共有)、embedding をホストへ(約 1.3 GB = 約 90 slot)。
4. 最初の大きな prefill の前後でキャッシュを縮めて戻す。
