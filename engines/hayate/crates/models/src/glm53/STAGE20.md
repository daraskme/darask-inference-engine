# 第20段階: 文脈に合わせたエキスパート配置(phase20/glm53pl)

基点は phase19/glm53d 3754d00(第19段階 + serve の device 経路・GPTQ 重み)。
計測は `spill/glm53d/b`(`one.sh` / `driver.sh`)、シミュレータは `spill/glm53d/place_sim.py` / `place_sim2.py`。

## 1. 何が遅かったか

第19段階の未計測だった長文脈の decode を流したところ(device、88 GiB 相当、`bench.txt` = Rust のソース):

| 条件 | decode tok/s | GPU hit | CPU ms/token |
|---|---:|---:|---:|
| 短いプロンプト("Write a Rust function…"、第19段階) | 28.4 | 0.824 | 23.9 |
| コード 512 + 512 トークン(`code1k`) | 10.98 | **0.480** | 78.1 |
| コード 32K + 512(`long32`) | 10.58 | 0.463 | 80.7 |
| 同(`long32r`、別の回) | 11.51 | 0.488 | 74.6 |
| 同、第18b段階の sync 経路(`long32sync`) | 10.70 | | (CPU 39.97 GB/s) |
| 128K(32,000 を prefill して潜在 KV・索引プールを 4 倍に複製、`long128`) | 11.48 | 0.458 | 75.2 |

device と sync はミスが支配的な長文脈でも同等(device の退行なし)。ただし CPU の実効帯域は device 経路の報告が
31.6〜32.6 GB/s、sync が 40.0 GB/s。device 側の `cpu_ms` は mailbox(mapped)からの入力読みと出力書きを含むので
定義の差の可能性もあるが、同じ量のミスで約 20% 遅いなら 32K で約 15 ms/トークン分になる。別途調べる。

32K のプロファイル(`long32p`、eager + event): attention 8.34 / router 1.53 / GPU エキスパート 2.87 /
sparse 選択 0.46 / sparse MLA 0.95 / head 0.47 ms、**CPU 待ち 77.7 ms**。GPU 経路は短い文脈(約 13.8 ms)と
ほぼ同じで、文脈長そのものの費用は小さい。128K(`long128p`)でも attention 8.17 / sparse 選択 0.73 / sparse MLA 0.86 ms、
CPU 待ち 81.1 ms。sparse 選択は 32K → 128K で 0.46 → 0.73 ms(+0.27 ms)だけ。遅さは全部ミス(ヒット率)。1K でも同じなので、原因は文脈長ではなく
**起動時の頻度(`glm53-stage6/frequencies.bin`)がコード生成のルーティングに合わないこと**と、decode 中の保守
(64 トークンの窓、1 スワップ/トークン)が追いつかないこと。prefill のルートは `cache.route()` に入るが、
prefill 1 回が窓の 1 要素にしかならない。

## 2. シミュレーション(実測と一致)

`--save-routes` を agent-turn bench でも取れるようにし(`glm_bench_trace prefix_words / turn_words` で区切りを出す)、
現在の保守を再現するシミュレータで方式を比べた。現行方式の再現値は実測と一致(code1k 0.4804 = 0.4804、
long32r 0.4882 = 0.4882、短いプロンプト 0.810 対 実測 0.824)。

prefill の終わりに、直近 N トークンのルート(トークンあたりの回数)で順位を付け、上位を GPU に置く(上限なし):

| trace | 現行 | N = 256 | N = 4096 | N = 全部 | 未来の decode を知る静的配置(上限の目安) |
|---|---:|---:|---:|---:|---:|
| code1k(slot 5,770) | 0.480 | **0.819** | 0.814 | 0.814 | 0.923 |
| code8k(slot 5,759、実測 11.89 tok/s・0.4835) | 0.4835 | **0.842** | 0.837 | 0.834 | |
| long32(slot 5,662) | 0.488 | 0.696 | 0.728 | **0.748** | 0.903 |

窓は長いほうが 32K で効き、短い文脈では差が小さい(0.008 以内)ので既定は 32,768 トークン。

- 交換数は 1,800〜2,900 組(各方向 26〜41 GB)。起動時頻度との混合(beta 0.8)はどちらでも悪い。
- 起動時頻度を量子化トラックの calib コーパス(日本語 chat・tool call・コード)のものに替えると code1k は
  0.73 になるが、短い英語プロンプトが 0.81 → 0.63 に落ちる。固定の頻度ではどの用途にも合わない。
- decode 中の保守を強くしても(最大 2〜16 スワップ/トークン、窓 16〜64)ヒット率は +0.003〜0.015 で、
  スワップの DRAM 往復(1 組 28 MB)が増える分 1 トークンの DRAM 量は増える。保守は今のまま。

## 3. プロンプトと返答が違うとき(エージェント)

プロンプトのルートで置くと、返答がプロンプトと似ていないときに逆効果になる。serve のエージェントループ
(e2e の `--bench`: 30K の定型コード風 filler + ツール定義、返答は日本語の方針と tool call)で、prefill の終わりに
全プロンプトで置くと decode が 12.5〜14.8 → 9.4〜9.7 tok/s に落ちた。同じ形のプロンプトで run のルートを取り
(`agent30r`、実測 hit 0.640)、方式を比べた(hit、括弧は交換数):

| 方式 | agent30 | code1k | code8k | long32 |
|---|---:|---:|---:|---:|
| 配置なし | 0.640 | 0.480 | 0.483 | 0.488 |
| prefill の終わりに全プロンプト | 0.578 | 0.812 | 0.835 | 0.754 |
| 同 + 起動時頻度 × 2 | 0.666 | 0.694 | 0.706 | 0.648 |
| 全プロンプト + decode 8 トークンで適応して置き直す | 0.737 (6,071) | 0.810 (3,133) | 0.835 (3,272) | 0.760 (3,324) |
| **prefill では置かず、decode 4 トークンで 1 回だけ置く** | **0.740 (272)** | 0.797 (2,802) | 0.825 (2,920) | 0.746 (2,919) |

最後の方式を採った。コードでは prefill の終わりに置く方式より 0.01 低いが、エージェントの入れ替えが 6,071 → 272 個、
複数ターンで毎回プロンプト向きに戻して返答向きに直す往復(約 3,000 個 × 2)が無くなる。

## 4. 変更

- `Experts::route` が MoE 層ごとに直近 `placement_tail`(既定 32,768)トークンのルートを持つ(prefill・decode とも)。
- prefill の終わり(`place_for_context`): 入れ替えはせず、保守の窓をリセットし、文脈の順位(beta × 直近ルートの
  トークンあたり回数 + (1 − beta) × 起動時頻度)とその上位 N 集合を持つ probe を始める。
- decode の各トークンの後(`probe_token`): `placement_probe`(既定 4)トークン目に、decode したトークンのルート/
  トークン数で 1 回置く。同点は、文脈の上位集合がその 4 トークンを今の集合以上に当てたなら文脈の順位、そうでなければ
  起動時頻度。上限なしで置くので結果は順位の上位 N に一致する(同点は頻度、次に番号)。
- 入れ替え(`place_scores`): 1 組 = 入る側の pinned RAM 画像を一時 GPU バッファへ H2D → 出る側の slot を同じ pinned
  バッファへ D2H(同じ stream なので順序どおり)。出た側の GPU バッファが次の組の受け皿になるので、確保は copy stream
  ごとに 1 画像だけ(第18段階の伸縮は画像ごとの cudaMallocHost で 2.2 GB/s)。各方向約 20 GB/s。使用中の画像は飛ばす。
- セッションのチェックポイントはルートの tail を持ち、復元で probe を始める。GPU 集合は戻さない(古い集合に戻すと
  新しい会話ごとに約 1.8 秒かかった)。そのため復元の続きは冷えた実行とビット一致とは限らない(CPU/GPU エキスパートの
  丸め差、相対 1e-4)。e2e は `restore_continues_cold`(先頭 16 文字以上一致)にした。ビット一致に戻すには CPU の行
  カーネルを GPU の一括 GEMV と同じ演算順にする(CPU 担当に依頼済み)。
- `maintenance_interval` 0(固定キャッシュ、試験用)では配置も probe もしない。
- `Options::{placement_tail, placement_beta, placement_swaps, placement_probe}`、CLI `--context-placement N`(0 で無効)/
  `--placement-beta` / `--placement-swaps` / `--placement-probe`。
- 試験 `glm53_context_placement_swaps_images`(GPU、checkpoint 不要): 上限つき・上限なしの入れ替えのあと全 slot と全
  RAM 画像の中身がそれぞれのエキスパートのもの、probe の判定と入れ替え。`glm53_device_decode_matches_sync`・
  `glm53_device_decode_session_and_budget` も通過。
