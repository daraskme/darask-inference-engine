# M0：計測と下調べの結果（2026-10-20）

[計画書](plan.md) §14 の M0 を、このマシン（RTX PRO 6000 Blackwell Workstation、RAM 125GB、NixOS）で実施した結果です。計画書と食い違う点は、この文書が優先です。

## 1. 計画書の修正点

一次情報（RadixArk NVFP4 チェックポイントのヘッダ、Transformers 5.17 の `qwen4_exp`）と照合して見つかったものです。

| # | 計画書 | 実際 | 影響 |
|---|---|---|---|
| 1 | PLE は「layer 2 だけ」 | `ple_layer_ids=[2]` は **1 始まり**。0 始まりでは **layer 1**（チェックポイントでも `layers.1.ple.*`） | 実行計画とカーネルの層番号 |
| 2 | QSA の圧縮ブロックは確定したトークンだけで作り、投機トークンでブロックを確定させない | 参照実装では、位置 p のクエリは **p 自身を含めて**完成したブロックを見る（`(p+1) % 4 == 0` で p のブロックが完成する）。検証パスで投機トークンのブロックを使わないと、投機なしの decode と出力が変わる | 検証パスでは、draft 窓の中で完成するブロックの圧縮キーを**一時領域で作って使い**、受理された分だけ常設のキャッシュに書く。GDN の遅延コミットと同じ考え方 |
| 3 | RadixArk NVFP4 は 186GB、PLE 表は自前で FP8 化 | **135GB**。NVFP4 なのは routed experts だけで、dense 部は BF16 のまま。PLE 表は**最初から FP8 E4M3**（`ple_embedding_dtype: float8_e4m3fn`、`weight_scale` 付き、128 分割） | PLE の FP8 化は不要。dense の MXFP8 化は自前（M1） |
| 4 | QSA の出力ゲート（詳細なし） | `q_proj` の出力 12288 はヘッドごとに [query 256 \| gate 256] の並び。ゲートは要素ごと（6144 個）の sigmoid | `qsa` カーネルの入出力レイアウト |
| 5 | GR の書き戻しは「本ごとのスカラー」 | スカラーは `2·sigmoid(inject(x̂)/4)`。読み出しは `sigmoid(up(silu(down(x̂)/4)))` を掛けて4本の平均。x̂ は本ごとの `(1+w)` RMSNorm | `gr_read` / 書き戻しの式 |
| 6 | PLE 層（詳細なし） | key_proj(2560→10240) と value_proj(2560→2560)。4本それぞれ「RMSNorm した残差と RMSNorm した key の内積 / √2560 → 符号付き平方根 → sigmoid」で value をゲートし、norm_conv → 10240 チャンネルの depthwise conv（k=4、dilation 3、状態 9 ステップ）→ SiLU を足して、attn 側 GR の**前**に残差の4本すべてへ加える | PLE カーネルの設計（M1） |
| 7 | 帯域 1.79TB/s で理論 290 tok/s | 実測のストリーミング読み出しは **1,605 GB/s**。6.1GB/トークンなら上限は **263 tok/s** | 目標 240 tok/s は実測帯域の 91%。目標は据え置くが、余裕はほぼない |
| 8 | 比較相手は llama.cpp、vLLM、SGLang | このマシンには **Hayate の Qwen3.8 実装**（stage 20b、2026-10-16）がある。投機なし 71〜77 tok/s、MTP で 110〜113 tok/s、prefill 約 2,200 tok/s。重み（`hyt/qwen38-nvfp4`）はもう削除済み | Hayate も同じマシンの比較対象にする。GDN の WY チャンク prefill や QSA の基数 top-k などは参考になる |
| 9 | MTP は transformers で検証 | transformers は MTP を実装していない（重み `mtp.*` はチェックポイントにある） | M3 の参照は SGLang の `qwen4_exp_mtp` |
| 10 | OS は Ubuntu | NixOS のまま。ツールチェーンは flake（CUDA 13.4、rustc 1.98、ドライバ 595.99）。IOMMU は無効、memlock 上限 8MB でも `cuMemHostAlloc` の 48GiB は問題なし | なし |

## 2. 実測（`tsumuji-bench`、生データは `results/m0.jsonl`）

### (1) 帯域・(5) L2 と共有メモリ

| 項目 | 値 |
|---|---|
| SM | 188、2,617 MHz |
| DRAM ストリーミング読み出し（4GiB） | **1,605 GB/s**（通常ロード）、1,573 GB/s（evict-first） |
| L2 | 128MiB（persisting 上限 80MiB）。112MiB までは約 8.2 TB/s、128MiB で 7.6 TB/s、160MiB 以上は DRAM 並み |
| 共有メモリ | 1ブロック 99KiB、1 SM 100KiB |

### (2) カーネル間の空白と PDL

依存したカーネルを graph に並べたとき（1ステップ = 188 ブロック）：

| 1ステップの重み | graph のみ | graph + PDL | 帯域だけで決まる時間 |
|---:|---:|---:|---:|
| 空のカーネル | 0.69 µs | **0.43 µs** | – |
| 0.73 MiB | 1.75 µs（28%） | 0.69 µs（72%） | 0.50 µs |
| 1.47 MiB | 2.15 µs（46%） | 1.00 µs（99%） | 0.99 µs |
| 2.94 MiB | 3.26 µs（61%） | 2.04 µs（98%） | 1.99 µs |
| 5.88 MiB | 5.11 µs（78%） | 3.93 µs（101%） | 3.98 µs |
| 11.75 MiB | 9.36 µs（85%） | 8.08 µs（98%） | 7.96 µs |

（％は実測ピーク帯域に対する割合）

**PDL で重みの読み込みを `griddepcontrol.wait` の前に出せば、1.5MiB 以上のカーネルでは境界の空白がほぼ消える。** graph だけでは 1〜3MiB 級の GEMV が 46〜61% にとどまる。0.7MiB 以下の小さい射影（GDN の a/b、shared ゲートなど）は隣のカーネルに融合する。megakernel（M6）は、PDL 込みで 85% に届かなかった場合の手段のままでよい。

### (3) W4A16 GEMV（NVFP4、1280×2560、バッチ1）

| | 時間 | 帯域 |
|---|---:|---:|
| graph | 3.23 µs | 571 GB/s（35%） |
| graph + PDL | 2.99 µs | 617 GB/s（37%） |

CPU の f64 参照との最大相対誤差は 1.75e-8（nibble の順序とスケールの扱いが正しいことを確認）。この素朴な実装（1 warp で 1 行、CUDA コアで復元）は帯域の 37% しか出ず、同じ大きさの PDL チェーン（99%）に遠く及ばない。**M1 の GEMV は計画どおり swap-AB の MMA 版にし、1 SM あたりの読み込み量を増やす**。

### (4) PLE 型のランダム gather（16行 × 160B / トークン）

| トークン数 | ホスト 8GiB 表 | ホスト 48GiB 表 | デバイスメモリ |
|---:|---:|---:|---:|
| 1 | 2.24 µs | **2.13 µs** | 0.92 µs |
| 16 | 7.05 µs | 5.92 µs | 1.02 µs |
| 256 | 73 µs（8.9 GB/s） | 70 µs（9.4 GB/s） | 1.1 µs |
| 16,384 | 4.7 ms（8.9 GB/s） | **6.8 ms（6.2 GB/s）** | 32 µs |

decode では 1 トークン約 2µs で、layer 0 の計算に完全に隠れる。prefill の 16K チャンクでは 6.8ms かかる（48GiB 表では GPU 側のページ変換の影響で 6.2 GB/s に落ちる）が、チャンク全体の計算（数百 ms）の 1〜2% で、別ストリームで layer 0 と重ねれば隠れる。**PLE 表をホスト RAM に置く設計はそのまま採用**。hugepage での確保は M1 で試す。

### (6) MMA の持続性能（レジスタのみ）

| 形式 | 命令 | TFLOPS |
|---|---|---:|
| BF16 | `mma.sync.m16n8k16` | 503 |
| FP8 e4m3 | `mma.sync.kind::f8f6f4.m16n8k32` | 1,000 |
| NVFP4（ue4m3 スケール / 16） | `mma.sync.kind::mxf4nvf4.block_scale.scale_vec::4X.m16n8k64` | 2,052 |

いずれも仕様上のピークどおり（BF16 は 1 SM・1 クロックあたり 1,024 flop）。

**prefill の精度方式への影響**：1トークンの計算量は約 12.6 GFLOP（routed experts 4.7、dense 7.3、attention 約 0.6）。30K tok/s には合計約 380 TFLOPS が要る。

- MoE を W4A16（BF16 MMA）、dense を W8A8（FP8 MMA）にした場合、MMA を 100% 使えても1秒あたり 0.5 秒分の計算になる（141/503 + 219/1000）。平均 50% の効率で、ちょうど 30K tok/s。
- MoE を W4A4 にすれば MoE 部分は 4 分の 1 で済む。

→ 既定は計画どおり W4A16 で作り、M4 で効率を測ってから、W4A4 を「速度優先モード」にするか既定にするかを KL で決める。

## 3. チェックポイント（`tsumuji-pack inspect` / `check-ple`）

置き場所：`/mnt/NVME4TB/darask-inference-engine/local/hayate/src/Qwen3.8-Flash-Next-NVFP4`（RadixArk/Qwen3.8-Flash-Next-NVFP4 @ 7b71922、使うものなので NVMe）。

419 ファイル、135.16 GB。`tsumuji-pack inspect` で、視覚部を除く全テンソル群の dtype と形状が期待どおりで、層ごとの本数（GDN 36、QSA 12、MoE 48、experts 24,576）もそろっている（ログ：`logs/pack-inspect.log`）。

| 区分 | GB | 形式 |
|---|---:|---|
| routed experts | 67.95 | NVFP4（`weight` U8 [行, K/2]、`weight_scale` e4m3 [行, K/16]、`weight_scale_2` と `input_scale` は F32 スカラー） |
| PLE 表 | 51.20 | FP8 e4m3、128 分割 × [2,500,012, 160]、テンソル全体で BF16 のスケール 1 個 |
| dense | 9.90 | BF16（embedding と lm_head 各 1.27 を含む） |
| MTP | 5.21 | **全部 BF16**。experts は 3 次元にまとめた形（`gate_up_proj` [512, 1280, 2560]、`down_proj` [512, 2560, 640]） |
| 視覚 | 0.90 | BF16 |

- `check-ple`：チェックポイントの乗数・各ヘッドの素数・オフセットが `tsumuji-model::ple` と完全に一致。表の行数 320,001,536 は 128 の倍数への切り上げまで一致。
- `linear_attn.A_log` は F32 ではなく BF16 で保存されている（計算は F32 で行う）。
- **MTP の experts は NVFP4 になっていない**（量子化の対象から `mtp.*` が外されている）。BF16 のままだと draft 1 トークンで experts だけで約 98MB 読むので、計画どおり NVFP4 で使うなら自前で量子化する（draft の精度は受理率にしか影響しない）。量子化すれば約 1.4 GiB。
- MTP の入力まわりは `pre_fc_norm_embedding` [2560]、`pre_fc_norm_hidden` [10240]（計画書 §12 のとおり 10240 幅全体の norm）、`fc_embedding` と `fc_hidden` が [2560, 2560]、独自の `hyper_connection_mixer` を持つ。

## 4. golden fixture（`python/golden_tiny.py`）

- Transformers 5.17 の `qwen4_exp` で、4層（GDN、GDN+PLE、GDN、QSA）、hidden 256 の乱数モデルを作り、重みを BF16 に丸めて float32 の CPU で実行。119 個の中間テンソルを `fixtures/tiny/` に保存（再生成できるので git には入れない）。
- 96 トークン（EOS の連続を含む）で、prefill 48 トークン + 1 トークンずつの decode と、全体を一度に流した結果のロジットの差は **1.4e-6**。GDN と conv の状態、PLE の n-gram 文脈、QSA の圧縮キーについて、参照実装のキャッシュの扱いが一貫していることを確認した。
- Rust の PLE ハッシュ（`tsumuji-model::ple`）は、この fixture の 1,536 行（96 トークン × 16 ヘッド）すべてでビット一致（`cargo test -p tsumuji-pack`）。

## 5. M1 への持ち越し

- 実次元の golden：縮小 config では、形状をコンパイル時定数にしたカーネルを直接は試せない。チェックポイントの先頭数層（dense は BF16、experts は NVFP4 を復元、PLE は FP8 表から Python で gather）で、実形状の fixture を作る。
- 参照の BF16 原本（360GB）は KL 計測に要る。使う頻度が低いので、置き場所は `/mnt/SSD16TB/hayate/src/Qwen3.8-Flash-Next`（ユーザーの方針：使わないものは SSD16TB）。ダウンロードは M1 の開始時に確認してから行う。
- dense の MXFP8 化（自前、オフライン）、swap-AB GEMV、GDN 遅延コミット、QSA（修正点 2 を反映）。
