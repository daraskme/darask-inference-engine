# M2：decode の高速化（2026-10-20、進行中）

M1 の 78〜84 tok/s から、**148〜155 tok/s**（1ステップ 6.5〜6.75ms、投機なし）まで来ました。計画の目標 240 tok/s（4.17ms）にはまだ届いていません。品質は M1 と同等です（§3）。

## 1. 入れたもの（効果の大きい順）

| 変更 | 1ステップ | 内容 |
|---|---:|---|
| （M1） | 12.6ms → | 融合なし、graph なし |
| CUDA Graph + 全カーネル PDL | 10.6ms | 位置・トークン・PLE の文脈を GPU 側に持ち、1ステップを graph に取り込んで再生。GEMV は重みの先読みを `griddepcontrol.wait` の前に出す新カーネル（行数 R、先読み P、K 分割 S を形状ごとに選ぶ） |
| experts の shared memory バンク競合を解消 | 9.35ms | 1行を 16 レーンで分担すると、全レーンが x を 128B おきに読み、同じバンクに当たっていた（16 倍の直列化）。x を 32 要素ごとに1要素の詰め物を入れて並べる（`x32`）。単体で 47 → 28µs/層 |
| **dense を MXINT8 に** | 6.75ms | §2。GDN・QSA・GR・shared expert・PLE・lm_head の射影を、int8 ＋ 32 要素ごとの2のべきスケールに。router は BF16 のまま |
| GDN の再帰カーネルを作り直し、conv＋準備＋再帰＋ゲート付き正規化を1カーネルに | 6.5ms | lane = value 列、warp = key 行の組で、状態の読み書きを coalesced に（Sol の指摘）。conv の状態は位置の偶奇で2面を切り替え、複数ブロックが同じ q/k を読んでも競合しない |
| QSA の準備と密な範囲の attention を1カーネルに | （ばらつき内） | 位置が全トークンを見られる間（p ≤ 2050）は、query head のブロックが自分で現在トークンの K/V を計算して直接 attention する（Sol の「次版」の形）。スコアと選択のカーネルはすぐ終わる |
| その他 | – | 融合（GR の正規化を down 射影の取り込みに、GR の up と読み出しを1カーネルに、split-K の部分和は使う側で加算、残差を書くカーネルが次の正規化用の二乗和の部分和を出す）、router の top-k を1 warp に、shared expert を routed と同じカーネルに |

縮小モデルでの通しテストは、どの段階でも 96 位置で KL ≤ 1e-13（BF16 dense のとき）。graph 再生と直接起動はビット単位で一致。

## 2. dense の形式：MXFP8 ではなく MXINT8

計画は MXFP8（e4m3）でしたが、測定の結果 **MXINT8**（int8、OCP MX の形式）を既定にしました。バイト数も decode の計算コストも同じで、量子化誤差が小さいからです。

| dense の形式 | 速度 | KL（BF16 原本の FP32 参照と） | dense の量子化だけの KL（BF16 dense のエンジンと） |
|---|---:|---|---|
| BF16 | 107 tok/s（当時） | 0.059〜0.089 | – |
| MXFP8 | 150.6 tok/s | 0.072〜0.118 | 0.026〜0.066 |
| **MXINT8** | 145.5 → 148 tok/s | **0.060〜0.092** | **0.015〜0.035** |

（KL 平均の範囲は ja / en / code / long の4系列。§5 の読み込み時の競合を直したあとに測り直した値）

- 重みの誤差の最悪値（ブロック最大値比）は MXFP8 5.9%、MXINT8 0.78%（`tests/mxfp8.rs`、CPU の f64 と照合）。
- int8 の値 × 2のべき は BF16 でも FP32 でも誤差なしで表せるので、prefill を BF16 MMA の W8A16 でやる場合も誤差なしで復元できる。W8A8 の FP8 MMA は使えなくなるが、それは M4 で判断する。
- int8 → float は I2F 命令（スループットが 1/4）を使わず、バイト並べ替え（PRMT）＋FMA で誤差なしに変換している。
- `TSJ_DENSE=none` で BF16、`TSJ_DENSE_FMT=fp8` で MXFP8 に戻せる。

## 3. 品質

量子化を含めた品質は、BF16 原本との KL で 0.06〜0.09。BF16 dense のときも同じ大きさなので、大きい部分は RadixArk の NVFP4 experts（と FP8 の PLE 表）から来ている。ただし dense の MXINT8 単独でも KL 0.015〜0.035 あり、KL は足し算にならないので、内訳を断定はできない（Sol の指摘）。品質を上げるなら、experts の量子化の差し替え（QAD 版の `nvidia/Qwen3.8-Flash-Next-FP4-Local` や RedHatAI 版との比較、または計画の M6 の自前の GPTQ 型）が本筋。

## 4. 1ステップの内訳（`tsumuji bench`：その処理を graph から外すと縮む時間）

MXINT8、GDN 融合後、短い文脈、1ステップ 6.5ms（実行ごとに ±3% ほどばらつく）：

| 処理 | 縮む時間 | バイトからの下限 |
|---|---:|---:|
| mixer の入力射影（GDN 16480×2560、QSA 13952×2560） | 1.5ms | 1.25ms |
| experts（routed NVFP4 ＋ shared） | 1.44ms | 0.97ms |
| GR の down と up（97回） | 1.07ms | 0.40ms |
| mixer の出力射影 | 0.55ms | 0.47ms |
| GDN の中間（融合カーネル、36層） | 0.49ms | 0.13ms |
| QSA の中間（準備、スコア、選択、attention、12層） | 0.38ms | 小さい |
| lm_head、router、書き戻し、MoE の合流 | 0.3 / 0.24 / 0.16 / 0.12ms | – |

GEMV だけを残すと 3.0ms（下限 2.35ms）。残りの約 3.5ms は、層ごとに依存した処理の鎖の待ち時間（DRAM や L2 の往復、ブロック内の同期）が大半で、カーネルの起動回数そのものではない。GDN の3カーネルを1つに融合しても 0.05ms しか縮まなかったことからも、境界の数ではなく、直列の待ち時間が支配的と分かる。

## 5. 見つけて直した不具合：読み込み時の競合

MXINT8 への変換カーネルは NON_BLOCKING のストリームで動くが、変換元の BF16 はレガシーストリームの同期コピー（pageable からのコピーは DMA の完了前に返ることがある）で送っていた。変換が古い値を読むことがあり、**プロセスごとに出力が変わった**（同じプロセス内の繰り返しは一致）。変換の前にコンテキスト全体を同期して解消し、プロセスをまたいだ8回の実行（PDL と graph の有無の4通り × 2回）で、ロジットがバイト単位で一致することを確認した。`tsumuji detcheck` は、カーネルごとに PDL を外して決定性を調べるコマンド。

## 6. 試して採らなかったもの

- **PDL の通知を wait の前に出す**（Sol の提案）：差なし（6.94ms 対 6.94ms）。
- **int8 専用の GEMV の割り振り**（単体ベンチの最良）：エンジンでは遅くなった（6.50 → 6.82ms）。単体ベンチは split-K の部分和を別カーネルで足すが、エンジンでは使う側が足すので、分割数を増やす損が小さい。割り振りは BF16 で決めたものを両形式で使う。

## 7. この先

1. 残る待ち時間の鎖を削る：QSA の短い文脈用の経路（スコアと選択を飛ばし、準備と attention をまとめる）、experts の shared スロットの扱い、GR の部分和の数を減らす、など。
2. persistent カーネル（計画の M6）は、層ごとの待ち時間を重ねられる唯一の手段なので、1層単位で試す価値がある。
3. **M3（MTP 投機）**：1ステップで複数トークンを検証すれば、この固定の待ち時間を複数トークンで分け合える。投機なしで 240 tok/s を狙うより、伸びしろが大きい。
