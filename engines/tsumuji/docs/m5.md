# M5（一部）：OpenAI 互換 API サーバと、Hayate serve 向けのライブラリ（2026-10-21）

計画の M5 のうち、1ユーザーで使う部分を作りました。最終的には Hayate Studio から使うので、配線は hayate-serve の約束（hayate-studio の `docs/hayate-serve.md` §1–2、`apps/server/src/modules/llm/client.ts`）に合わせ、HTTP 以外の処理（トークナイザ、チャットテンプレート、ツール呼び出しと思考の分離、usage と timings、プレフィックスの再利用）は、serve から HTTP なしで呼べるライブラリにしました。外部 crate はありません。複数ユーザー（バッチ）と、複数の会話を同時に保つ KV はまだです。

## 1. 起動

```bash
nix develop -c cargo build --release -p tsumuji-server
```

```bash
nix develop /mnt/NVME4TB/darask-inference-engine/engines/hayate#default -c bash -c 'NEED=80 LABEL="Tsumuji API" scripts/gpu-run.sh -- target/release/tsumuji-serve --model /mnt/NVME4TB/darask-inference-engine/local/hayate/src/Qwen3.8-Flash-Next-NVFP4 --port 8090'
```

- 先にポートを開き、モデルを読み込む（約 55 秒）。読み込み中の `/health` は 503（`"status":"loading"`）を返し、届いたリクエストはキューで待つ。
- 既定のコンテキスト長は、モデルの上限（config.json の `max_position_embeddings`、262,144 トークン）か、起動時の空き VRAM に重みと並んで収まる長さの短いほう（4,096 の倍数）。KV と indexer のキャッシュは FP32 で 1 トークン 55.5 KiB（262,144 トークンで 14.2 GiB）。
- VRAM の実測（プロセス）：MTP 層を読む前のエンジンで 262,144 トークン 83.8 GiB、MTP 層込みのエンジンで 131,072 トークン 78.8 GiB（262,144 トークンなら計算上 85.8 GiB）。上の `NEED=80` なら gpu-run が 82 GiB 空くのを待ってから始まり、既定のコンテキストは 15 万トークン前後以上になる。GPU がほかに空いていれば `NEED=88` で上限まで入る。
- 空き VRAM からの計算は、エンジン以外を実測した定数（`server.rs` の `auto_ctx`）による見積もり。エンジンの使う量が変わるとずれる（MTP 層が増えたときは 1 回 OOM になった）ので、エンジン側で重みの後に決められるようにすることを親セッションに依頼した。`--ctx` を付ければその値を使う。
- 止めるときは Ctrl-C（またはプロセスに SIGTERM）。

| オプション | 既定 | 内容 |
|---|---|---|
| `--model DIR` | （必須） | チェックポイントのディレクトリ（tokenizer.json、generation_config.json もここから読む） |
| `--host` / `--port` | 127.0.0.1 / 8090 | 7880 は Hayate の serve |
| `--ctx N` | 収まる最大（上限 262,144） | プロンプトと生成の合計の上限 |
| `--name ID` | qwen38 | `/v1/models` と応答の `model`（Hayate serve での id。リクエストの `model` は何でも受け付ける） |
| `--drafts auto\|K` | auto | MTP の下書きの数。auto はエンジンが直近の受理率からステップごとに選ぶ（`spec_auto`）。K で固定（1 ステップで K+1 トークンまで確定）、0 で 1 ステップ 1 トークン |
| `--host-sampling` | オフ | すべてのリクエストをホストでサンプリングする（デバッグ用） |
| `--qwen2-regex` | オフ | transformers 5.x と同じ pre-tokenizer の正規表現を使う（§4） |
| `--dry-run` | オフ | GPU を使わず、決まった文（tools 付きのリクエストには決まったツール呼び出し）を一定の速さで返す。プレフィックスの再利用は本物と同じ帳簿で動く |

補助のサブコマンド：`tsumuji-serve encode --model DIR [--chat [--think]] < text`（`python/tok.py` の代わりにトークン id を出す）、`decode`、`check`（§4）。

## 2. 対応範囲

`GET /health`、`GET /v1/models`（`/v1/models/{id}`）、`POST /v1/chat/completions`、`POST /v1/completions`。

| パラメータ | 内容 |
|---|---|
| `messages` | system / user / assistant（`tool_calls`）/ tool。content は文字列か text パーツの配列。`tool_calls[].function.arguments` は JSON の文字列でもオブジェクトでもよい。assistant の `reasoning_content`（`reasoning` でも可）はテンプレートどおりプロンプトに戻す。`developer` は system として扱う |
| `tools`、`tool_choice` | OpenAI の function 定義。テンプレートの tools 部分に描画し（`tojson` は Python の `json.dumps` と同じ書式）、出力の `<tool_call>` を `tool_calls` にする（§3）。`tool_choice` は auto と none だけ |
| `stream` | SSE（OpenAI の chunk 形式）。最初に role の chunk、最後の chunk に finish_reason と `usage` と `timings`（`stream_options` によらず常に）、`data: [DONE]` |
| `max_tokens` / `max_completion_tokens` | 既定は chat が「コンテキストの残り」、completions が 16。入らないときは応答の前に 400 `prompt (N tokens) + max_tokens (M) exceeds server context (C tokens)`（Studio はこの文から max_tokens を縮める） |
| `temperature`、`top_p`、`top_k`、`min_p` | 既定は generation_config.json（1.0 / 0.95 / 20）。temperature 0 は greedy。top_k は 0 か -1 でオフ |
| `seed` | サンプラの乱数。同じ seed なら同じトークン列になる（エンジンの引き方は seed・位置・ロジットだけで決まる）。省略時はリクエストごとに変える |
| `stop` | 文字列かその配列。止めた文字列は出力に含めない |
| `presence_penalty`、`frequency_penalty`、`repetition_penalty` | ホストで適用（vLLM と同じ定義）。これと `min_p` を使うリクエストは、ロジットをホストへ写して選び、投機なしで 1 トークンずつ進む |
| 思考の切り替え | トップレベルの `enable_thinking`、`preserve_thinking`、`reasoning_effort`（Hayate serve の形）と `chat_template_kwargs` の同名（vLLM / SGLang の形。両方あればこちら）。`reasoning_effort` は none・minimal で思考オフ、low、medium、high・xhigh・max は xhigh。`reasoning_budget` は受け付けるが、まだ効かない |
| `separate_reasoning` | false にすると `<think>` を分けない（SGLang と同じ名前） |
| `ignore_eos`、`stop_token_ids`、`skip_special_tokens`、`return_token_ids` | vLLM と同じ拡張。`return_token_ids` は非ストリーミングで `prompt_token_ids` と `choices[0].token_ids` を返す |
| `echo`（completions） | プロンプトを出力の前に付ける |

- **usage**：`prompt_tokens`、`completion_tokens`、`total_tokens`、`prompt_tokens_details.cached_tokens`（スナップショットから戻したプロンプトのトークン数）。EOS のトークンも completion_tokens に数える。
- **timings**（応答・最後の chunk のトップレベル）：Hayate の `prefill_ms`（キャッシュ以外の部分）、`decode_ms`、`decode_tok_s`、`mtp_accept`（投機の 1 ステップで確定したトークン数の平均。最初のステップは除く。`spec_auto` は受理が悪いと下書きを減らすので、この値は受理率ではない）と、`queue_ms`、`prefill_tok_s`、`sampling`（greedy / device / host）。
- **ストリームの途中のエラー**：`data: {"error":{…}}` を最後に送り、`[DONE]` なしで接続を閉じる。
- 停止：generation_config.json の `eos_token_id`（`<|im_end|>` 248046、`<|endoftext|>` 248044）と stop 文字列。
- 思考の分離：思考オンのとき、プロンプトは `<think>\n` で終わるので、出力は `</think>` までを `reasoning_content`、その後を `content` に分ける（SGLang / vLLM の Qwen3 用パーサと同じ）。reasoning は前後の空白を、content は先頭の空白を落とす。ストリーミングでは `</think>` の途中や末尾の空白だけを保留するので、ストリーミングと非ストリーミングで同じ文字列になる。`</think>` が出ないまま終わった分はすべて reasoning。
- 同時に処理するのは1リクエストで、ほかは FIFO で待つ（`/health` の `queued`）。クライアントが切断すると、生成中なら次のトークンで、プロンプトの処理中なら 256 トークンごとの区切りで、キュー待ちならその場で止める（ソケットを 100ms ごとに確認）。
- 1リクエストにつき stderr に1行：プロンプト（うちキャッシュ）と生成のトークン数、終わり方、prefill と decode の tok/s、キューの待ち時間、ホストでサンプリングしたときはトークンあたりのロジットのコピーとサンプリングの時間。

**対応していないもの（400 を返す）**：`functions` / `function_call`（古い形）、`tool_choice` の required と関数指定、`n` > 1、`logprobs`、`response_format`（json）、画像・音声のパーツ、completions の `suffix` と `best_of` > 1。知らないパラメータは無視する。

## 3. ライブラリの構成（serve から使う部分）

`tsumuji_server` は HTTP サーバ（`api`、`http`、`server`）と、それを使わずに呼べる部分に分かれている。serve に組み込むときに使うのは後者だけ：

| モジュール | 内容 |
|---|---|
| `model::TextModel` | トークナイザ、generation_config の既定値、EOS、コンテキスト長。`TextModel::load(dir, name)` |
| `request` | リクエストの JSON → `Prepared`（プロンプトの ids、サンプリング、上限、stop、思考の分離とツールの有無、スナップショットを取る位置）。エラーは `ApiError { status, message }` |
| `chat`、`tools` | チャットテンプレート（tools 込み）と、出力のツール呼び出しの解析 |
| `generate` | エンジンとの境界 `trait Generator`、`PrefixCache`（§5）、`EngineGen`（今のエンジン） |
| `output::Output` | 生成トークン → `Piece { reasoning, content, tool_calls }`（detokenize → stop → 思考の分離 → ツール呼び出し）と finish_reason（stop / length / tool_calls） |
| `wire` | OpenAI / Hayate serve の JSON（chunk、最後の chunk、非ストリーミングの応答、`Usage`、`timings`、エラー） |

1リクエストの流れ（`server.rs` の `run_job` と `api.rs` の `run` がこのとおりに書いてある）：

```rust
let p = request::parse_chat(&model, &body_json, seed)?;
let mut out = output::Output::new(&p, id);
let stats = engine_gen.generate(GenRequest { prompt: &p.prompt, params: &p.params, max_new: p.max_new, marks: &p.marks },
    &mut |t| { let (flow, piece) = out.token(&model.tok, t); send(meta.delta_chunk(&piece, p.reasoning)); flow },
    &|| client_gone())?;
send(meta.delta_chunk(&out.finish(), p.reasoning));
send(meta.final_chunk(out.finish_reason(), Usage { prompt: p.prompt.len(), completion: stats.generated, cached: stats.cached }, wire::timings(&stats, p.prompt.len(), queue_s)));
```

ツール呼び出しの出力：テンプレートが教える形は `<tool_call>\n<function=名前>\n<parameter=引数>\n値\n</parameter>\n</function>\n</tool_call>`。`</tool_call>` まで来たら `tool_calls` を1つにまとめて送る（Hayate serve と同じく、引数の差分のストリームはない）。引数の値は、ツール定義の型に合わせて vLLM の qwen3_coder パーサと同じ規則で変換する（string はそのまま、integer / number / boolean は解釈、object / array は JSON、`null` は null、定義にない引数は文字列）。`<tool_call>` の前の空白は落とし、閉じないまま終わった呼び出しは本文として返す。

## 4. トークナイザとチャットテンプレート

| 部分 | 内容 |
|---|---|
| `tokenizer.rs` | tokenizer.json の byte-level BPE。追加トークン（33 個）を最長一致で先に切り出し、残りを NFC → pre-tokenizer → BPE（`tokenizers` の `Word::merge_all` と同じ優先度付きキューと同順位の扱い）。decode はトークンごとに完成した文字だけを返し（`DecodeStream`）、壊れた UTF-8 は `from_utf8_lossy` と同じ位置で U+FFFD にする |
| pre-tokenizer | 正規表現エンジンは使わず、Oniguruma の「左から順に最初に当たる選択肢」と同じ結果になる照合を手で書いた（`'s` 類の大文字小文字無視は `ſ` も含む） |
| `unicode.rs`、`unicode_data.rs` | 一般カテゴリ（L / M / N）、`\s` と Python の `isspace`、NFC。表は `python/gen_unicode.py` が Python の unicodedata（Unicode 16.0）から生成 |
| `chat.rs` | chat_template.jinja を手で書き写したもの（system、user、assistant と tool_calls、tool、tools の定義、`enable_thinking`、`reasoning_effort`、`preserve_thinking`、Jinja の `trim` と同じ空白の定義、`tojson` は `json.dumps` と同じ書式で整数と小数も区別）。テンプレートが例外を出す入力ではエラーを返す |

**transformers 5.17 との違い（見つけたこと）**：transformers の `Qwen2Tokenizer` は tokenizer.json の pre-tokenizer を読まずに、古い Qwen2 の正規表現（`\p{L}+`、結合文字 `\p{M}` を含まない）で上書きする。モデルに同梱の tokenizer.json と tokenizer_config.json の `pretokenize_regex` はどちらも `[\p{L}\p{M}]+` なので、結合文字（デーヴァナーガリーやタイ語の母音記号、アラビア語の母音符号、NFC で合成されないアクセントなど）を含む文字列では、AutoTokenizer とモデル本来のトークン化がずれる。日本語・英語・コードではずれず、eval/*.ids もどちらの方式でも同じ id に戻る。サーバの既定はモデル本来の tokenizer.json の方式にし、`--qwen2-regex` で transformers 5.x と同じにできるようにした。

照合は `python/check_text.py` が transformers（と `tokenizers.Tokenizer.from_file`）でケースを書き出し、`tsumuji-serve check` が比べる：

```bash
nix develop /mnt/NVME4TB/darask-inference-engine/engines/hayate#tools -c python3 python/check_text.py /mnt/NVME4TB/darask-inference-engine/local/hayate/src/Qwen3.8-Flash-Next-NVFP4 /tmp/cases.json
nix develop -c target/release/tsumuji-serve check --model /mnt/NVME4TB/darask-inference-engine/local/hayate/src/Qwen3.8-Flash-Next-NVFP4 /tmp/cases.json
```

| 項目 | 件数 | 結果 |
|---|---:|---|
| encode（tokenizer.json の方式 vs `tokenizers`） | 444 | 全一致 |
| encode（`--qwen2-regex` vs AutoTokenizer） | 444 | 全一致（このうち 10 件は2つの方式で id が違う） |
| eval/*.ids を decode して encode し直す（両方式） | 8 | 全一致。transformers 自身も元の ids に戻る |
| decode（全体とストリーミング、特殊トークンを除く／除かない） | 1,504 | 全一致 |
| チャットテンプレート（文字列、両方式の ids。tools と tool_calls の 5 件、テンプレートのエラー 6 件を含む） | 35 | 全一致 |

encode のケースは、手で書いた 41 個（日本語、英語、コード、絵文字、特殊トークン、空白の種類、NFC、ほかの文字体系、`'s` 類）、ランダムな文字列 400 個、ソースと文書のファイル。decode は eval のファイルと、UTF-8 の途中で切れるバイトトークンを多く含むランダムな id 列 300 個。tools のケースは、日本語の説明、整数と小数（`1e3` は `1000.0`）、配列・オブジェクト・真偽値の引数、1回に2つの呼び出し、tool の応答の連続を含む。encode は 8〜11M 文字/s。

## 5. プレフィックスの再利用

エージェントは毎ターン会話全体を送るので、前のリクエストと共通の先頭の状態をスナップショットから戻し、残りだけを prefill する（`generate.rs` の `PrefixCache`）。エンジンの `save_state` / `restore_state` を使う（GDN の再帰状態と conv、PLE の文脈、位置などを GPU 上でコピー。KV と indexer のキャッシュはコピーせず、その位置より前は上書きされるまで有効）。

- KV の領域は1つなので、全スナップショットは「今 KV にあるトークン列」の先頭部分。その列を記録しておき、新しいプロンプトとの共通部分より長いスナップショットは捨てる。
- 戻すのは、新しいプロンプトの先頭と一致する最長のスナップショット（ロジットのため、プロンプトの最後の1トークン以上は流す）。なければ reset。
- スナップショットを取る位置：
  1. **プロンプトの最後のターンの始まり**（最後の `<|im_start|>`）。Studio は `reasoning_content` を送り返さないので、前のターンの生成プロンプト `<think>\n`（トークン 198）は、次のリクエストでは `<think>\n\n</think>`（271）に描き直され、生成の終わりのスナップショットは使えない。会話履歴の部分はそのまま戻ってくるので、ここで取ったものが使える。
  2. プロンプトの終わり。
  3. 生成の終わり（思考オフで、答えがそのまま履歴に戻るとき）。
- 最大 8 個（1 個で GPU を約 110 MiB）。1 回の保存は同期を含めて 5〜7 ms（同じ長さのプロンプトの prefill 時間の差からの推定）。
- 「直近 4 本の会話を保つ」（KV の領域を複数持つ）はエンジン側の作業が要るので後で。`PrefixCache` は領域ごとに持てば広げられる。

## 6. 実モデルでの確認

- greedy（temperature 0）の chat の答えが、同じチャットテンプレートの ids で `tsumuji run` が出すトークンと一致した（日本語・英語とも 64 トークン、プロンプトの ids も `python/tok.py` と一致）。MTP 層とスナップショット、デバイスでのサンプリングが入った今のエンジンでも同じトークンになる。
- プレフィックスの再利用：思考オフの2ターン目は 61 トークン中 37 を戻し（生成の終わりのスナップショット）、その答えは、キャッシュを消してから同じリクエストを最初から流したときと greedy のトークンが一致した。思考オン（low）で reasoning を送り返さない2ターン目は 98 トークン中 49（最後のターンの始まり）。ツールの結果を返したリクエストは 406 中 364。
- ツール呼び出し：`openai` クライアント（`python/api_smoke.py`）で、モデルが `read_file {"path": "README.md", "limit": 20}`（limit は定義どおり整数）を呼び、ストリーミングの `delta.tool_calls` と finish_reason `tool_calls` を返した。結果を tool で返した続きも動く。
- curl でストリーミングと非ストリーミング、`openai` クライアントで、日本語と英語、思考のオン・オフと `reasoning_content`、複数ターン、completions を確認した。Hayate の tools シェルには `openai` がないので、flake.lock の nixpkgs から `python3.withPackages (p: [p.openai])` を作って使った（手順は `python/api_smoke.py` の先頭）。
- 切断（ストリーミング、非ストリーミング、プロンプトの処理中、キュー待ち）で生成が止まること、同時のリクエストが順に処理されることを確認した。
- **デバイスでのサンプリングと MTP の投機**（エンジンの `set_sampling` と `spec_auto`、その前は `spec_step(3)`）：greedy の答えは `tsumuji run`（1 トークンずつ）とトークンが一致し、同じ seed のサンプリングは同じトークン列を再現する。最初に試したエンジンでは temperature 1.0 / top_k 20 / top_p 0.95 のリクエストで GPU が止まったが、親セッションが直した版では同じリクエストが 0.25 秒で終わる。プレフィックスの再利用も投機込みで、キャッシュあり・なしのトークンが一致する。

## 7. 速度（API 経由、RTX PRO 6000）

### 今のエンジン（デバイスでのサンプリング、MTP の投機、コンテキスト 131,072）

| 条件 | `spec_auto`（既定） | k=3 固定 |
|---|---:|---:|
| greedy、日本語の質問、64 トークン | **170.5 tok/s** | 148.7 tok/s |
| greedy、英語の質問、64 トークン | 196.6 tok/s | 200.7 tok/s |
| greedy、Rust のコードと解説（chat、632 トークン） | 180.3 tok/s | 184.4 tok/s |
| greedy、日本語の長文（completions、1,024 トークン） | 138.0 tok/s | 131.1 tok/s |
| サンプリング T=0.6 / T=1.0（top_k 20、top_p 0.95）、同じ長文 | 136.2 / 135.8 tok/s | 121.9 / 124.0 tok/s |
| サンプリング T=1.0、思考 low の短い答え（18 トークン） | 215.8 tok/s | 234.5 tok/s |

prefill は 230〜340 tok/s（8 トークンずつ、スナップショット込み）。k=3 固定では、日本語の長文のように 1 ステップの確定が 2.2 前後だと投機なしの 1 トークンずつ（下の 3 回目で 133.2 tok/s）とほぼ同じで、英語やコードのように 3 前後なら 1.3〜1.4 倍だった。`spec_auto` は受理の悪い文で下書きを減らすので、日本語とサンプリングで速くなり、英語とコードはほぼ同じ（差は数 % で、測定のばらつきと同程度）。

### それ以前（参考）

測ったのは3回で、エンジンは回ごとに親セッションの作業で変わっている。1回目は GPU を Tsumuji だけが使い、MTP 層を読む前、コンテキスト 262,144。2回目は MTP 層込み、コンテキスト 131,072 で、別のプロセス（llama.cpp の heretic-eval）が同時に GPU を使っていた。3回目はスナップショット込み、投機なし、コンテキスト 131,072、heretic-eval が載っていた。

| 条件 | 1回目 | 2回目 | 3回目 |
|---|---:|---:|---:|
| greedy、短いプロンプト、64 トークン生成 | **145.3 tok/s**（同条件の `tsumuji run` は 147.9） | 135.3 tok/s | **146.2〜148.8 tok/s** |
| greedy、1,024 トークン生成 | 122.1 tok/s | 115.8 tok/s | 133.2 tok/s |
| ホストでサンプリング（top_k 20）、1,024 トークン | 107.1 tok/s（T=1、改良前のサンプラ） | 112.1 tok/s（T=1） | 129.2 tok/s（T=0.6） |
| ホストでサンプリング（top_k オフ、top_p 0.95）、512 トークン | 80.6 tok/s（改良前） | 101.8 tok/s | – |
| greedy、4,096 トークンのプロンプト、256 トークン生成 | 51.6 tok/s | – | – |
| prefill（8 トークンずつ） | 250〜300 tok/s（4,096 トークンで 16.5 秒） | 254〜278 tok/s | 210〜240 tok/s（スナップショット込み） |

- decode の tok/s は最初のトークン（prefill から出る）を除いた (生成数 − 1) / 時間。
- 4,096 トークンの後の 51.6 tok/s はエンジン自体の速さで、コンテキストを大きく取ったせいではない（`tsumuji run --ctx 8192` でも 48.5 tok/s）。
- 4,096 トークンのプロンプトの途中でクライアントが切れると、3.7 秒でエンジンが空いた（全部流すと 16.5 秒）。

**ホストでサンプリングする往復のコスト（トークンあたり。今は penalties と min_p のリクエストだけがこの経路）**：ホストでのサンプリングでは、ステップの完了を待つ → `Engine::logits()` で 1MB（248,320 × f32）をホストへ → サンプリング → `step(Some(tok))` が直列になり、その間 GPU は止まる。

| 内訳 | 時間 |
|---|---:|
| ロジットのコピー（pageable メモリへの 1MB） | 250〜380 µs |
| サンプリング（top_k 20、既定） | 1,115 µs → **42 µs**（1回の走査で上位 k だけを保つ。64 個ずつの塊を、しきい値を超える要素があるかだけで飛ばす） |
| サンプリング（top_k なし、top_p 0.95） | 4,828 µs → 1,636 µs（全体のソートをやめ、top_p を覆う先頭だけを並べる。残りは語彙の大半の exp） |
| サンプリング（top_k なし、top_p 1） | 1,555 µs（並べずに id 順で引く） |

投機なしの 1 トークンずつでは、ホストでサンプリングしても greedy より約 3 % 遅いだけだった（3回目で 129.2 対 133.2 tok/s）。今はデバイスで選ぶので、このコピーもない。

## 8. エンジンとの境界

サーバが見るのは `trait Generator` だけ：「このプロンプトを流し（キャッシュがあれば先頭は戻す）、止めると言うまでトークンを1つずつ渡す」。今のエンジンは `EngineGen` が包んでいる：`set_sampling` → `PrefixCache` を通したプロンプト（`restore_state` か `reset`、`prefill`、`save_state`）→ `spec_auto()`（`--drafts K` なら `spec_step(K)`）を繰り返し、確定したトークンを1つずつ `emit` に渡す（EOS・stop 文字列・max_tokens で途中から捨てても、状態には確定分がすべて入っているので、履歴にはそのまま記録する）→ 生成の終わりで `save_state`。コンテキストの終わりの 24 トークン（3 × N_MAX）では下書きを作らない（`spec_step(0)`。窓と下書きの位置が入らないため）。penalties と min_p のリクエストだけは `logits()` → ホストで選ぶ → `step(Some(t))`。テキストの処理（detokenize、stop、思考の分離、ツール呼び出し）はすべて `emit` の外側にある。

`--no-default-features` で、エンジンなしでもトークナイザ・テンプレート・HTTP・プレフィックスの帳簿のテストと `--dry-run` がビルドできる（エンジンを並行して直している間も試せるように）。
