# M1：正しく動く（2026-10-20）

バッチ1・投機なしの decode を、縮小モデルと実モデルの両方で参照と照合しました。プロンプトも decode を1トークンずつ回して処理します（本当の prefill は M4）。

## 1. 構成

| 部分 | 内容 |
|---|---|
| `tsumuji-engine` | config.json から次元を読み、同じコードで縮小モデルと実モデルを動かす。CLI は `tsumuji run / eval / kl` |
| 重みの置き方 | experts は NVFP4 のまま層ごとに1つのバッファ（expert e は `e × 27/16·F·H` バイト目）。dense は BF16 のまま、同じ入力を読む射影は1つの行列に連結（GR の down と inject、GDN の qkv・z・b・a、QSA の q・k・v・indexer、router と shared ゲート、shared の gate と up、PLE の key と value）。PLE 表（FP8、51GB）は pinned RAM に置いて GPU から直接読む |
| 計算精度 | 残差、活性、正規化、GDN 状態はすべて FP32。重みは BF16（dense）と NVFP4（experts、復元は誤差なし）。**KV と indexer のキャッシュは FP32**（§3） |
| カーネル | `kernels/decode/`：GEMV（BF16、NVFP4）、GR、GDN（conv、正規化、delta rule、gated norm）、QSA（準備、ブロックスコア、top-k 選択、attention）、PLE（gather、ゲートと dilated conv）、router、MoE の合流、argmax。次元は実行時の引数で受け取る |
| 読み込み | 52〜57 秒（PLE 表 20 秒、experts 26 秒、dense 9 秒）。VRAM 約 76GiB |

## 2. 縮小モデルとの照合（`tests/tiny_e2e.rs`）

`python/golden_tiny.py` が、experts を NVFP4、PLE 表を FP8 に量子化した縮小モデルを、RadixArk と同じテンソル名で書き出す。参照（transformers、FP32）も量子化後の値で計算するので、エンジンは実チェックポイントと同じ読み込み経路で、誤差なしに一致するはず。

- 96 位置すべてで greedy が一致。ロジットの最大差 1.5e-6、KL 最大 1.1e-13。
- 不具合が1つ見つかり、直した：トークン id を `cuMemcpyHtoD`（レガシーのストリーム）で送っていたため、NON_BLOCKING のエンジン用ストリームと同期せず、前のステップのカーネルが読む前に上書きされることがあった（実行ごとに結果が変わった）。ストリーム上の非同期コピーにし、読み込みの最後にコンテキスト全体を同期するようにした。

## 3. 実モデルとの照合（NVFP4 の重みを復元した参照）

参照は `python/reference.py`。transformers の `qwen4_exp` を1層ずつ GPU に載せて全系列を流す（BF16 の全体は VRAM に入らないため）。PLE 表は必要な行だけファイルから読む。評価の入力は日本語（ja）・英語（en）・Rust（code）各 512 トークンと、QSA の疎な選択が効く 4,096 トークンの長文（long）。

| 比較 | ja | en | code | long |
|---|---:|---:|---:|---:|
| BF16 計算の参照 vs FP32 計算の参照（参照どうし） | 3.3e-2 / 91.4% | 1.1e-2 / 97.5% | 2.5e-2 / 94.9% | 1.9e-2 / 94.2% |
| エンジン（BF16 キャッシュ）vs FP32 参照 | 1.6e-2 / 95.7% | 4.4e-3 / 97.9% | 9.4e-3 / 96.9% | 8.3e-3 / 95.9% |
| **エンジン（FP32 キャッシュ）vs FP32 参照** | **3.4e-11 / 100%** | **1.2e-3 / 99.6%** | **3.3e-11 / 100%** | **1.3e-3 / 99.0%** |

（KL 平均 / top-1 一致率）

- **このモデルは数値誤差にとても敏感**で、参照どうし（BF16 と FP32）でも KL が 0.01〜0.03 ある。
- FP32 キャッシュのエンジンは、ja と code の 512 位置すべてで FP32 参照と KL 1e-11 まで一致する。実装は正しい。
- en と long の残りは、それぞれ位置 370 と 1,194 で一度だけ起きた離散的な入れ替わり（router の同点に近い top-k と見ている）が、GDN の状態を通じて後ろに伝わったもので、それより前の位置はすべて 1e-6 未満。発散はしていない。
- KV と indexer のキャッシュを BF16 に丸めると KL が 0.004〜0.016 増える。品質を優先して **既定は FP32 キャッシュ**にした（256K コンテキストで VRAM +6GiB、decode は約 +0.03ms/トークン）。BF16 は `TSJ_NVCC_DEFINES=-DTSJ_KV_BF16` でビルドすれば選べる。

## 4. 速度（M1 時点）

融合なし・graph なし・PDL なしのまま、**78〜84 tok/s**（Hayate の投機なし 71〜77 tok/s を上回る）。4,096 トークンの文脈では 63 tok/s。

1ステップ 12.6ms の内訳（`tsumuji run --profile`、イベント記録の分を含む）：

| 処理 | ms | 割合 | 読むバイト | 帯域効率 |
|---|---:|---:|---:|---:|
| GDN（36層） | 3.71 | 29.5% | 4.16 GB | 70% |
| GR の読み出し（97回） | 2.84 | 22.6% | 1.28 GB | 28% |
| routed experts（48層） | 1.96 | 15.6% | 1.33 GB | 42% |
| QSA（12層） | 1.21 | 9.6% | 1.23 GB | 63% |
| router と top-k | 0.85 | 6.7% | 0.13 GB | 10% |
| lm_head | 0.78 | 6.2% | 1.27 GB | 100% |
| shared expert | 0.73 | 5.8% | 0.47 GB | 40% |
| MoE の合流、GR の書き戻し | 0.42 | 3.3% | – | – |

1トークンで読むのは約 9.9GB（dense が BF16 のため。計画の MXFP8 なら約 6GB）。実測帯域 1,605 GB/s での下限は 6.2ms で、M1 はその 49%。

## 5. M2 でやること

1. GEMV を作り直す。行の少ない行列（GR の down 324 行、router 513 行）は split-K で全 SM を使い、1スレッドあたりのロードを増やす。
2. 位置とトークンを GPU 側に持ち、1ステップ全体を CUDA Graph にして、全カーネルを PDL で起動する（重みは `griddepcontrol.wait` の前に読み始める）。
3. dense を MXFP8 にする（W8A16）。KL の増分を FP32 参照で測ってから採用する。
4. 小さいカーネルを融合する（router の top-k を並列化、合流と書き戻しと次の正規化をまとめる）。
