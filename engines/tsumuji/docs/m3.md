# M3：MTP 投機デコード（設計、2026-10-21）

Sol の第2回レビュー（`reviews/20261020-2305-latency-mtp.md`）の設計をもとにしています。

## 1. 目的と見積もり

投機なしの1ステップは約 6.5ms で、その半分以上は層ごとの依存した処理の待ち時間。N トークンを1回で検証すれば、重みの読み出しと待ち時間を N トークンで分け合える。

```
実効 ms/token = (T_draft(k) + T_verify(k+1) + T_commit) / E[受理数 + 1]
```

比較の相手は qwenfast（SGLang、RedHatAI NVFP4、厳密な MTP）の単独 264.5 tok/s（temperature 1.0、4,096 トークン生成の平均）。

## 2. 方針：全カーネルを N トークン対応にし、通常の decode は N = 1

- 1回のステップで N ≤ 8 トークン（位置 p .. p+N-1）を処理する。通常の decode は N = 1 で、同じコード。
- **トークンごとの計算順は N に依存させない**（split-K の分け方、レーンの分担、和の順序を固定）。これで「draft が全部正しいときの検証」と「1トークンずつの decode」がビット単位で一致し、テストできる。
- GEMV は重みを1回読んで N 列に掛ける。トークンを grid の次元に並べるだけでは重みの読み出しを共有できない。

## 3. 検証と確定の境界

確定済みの状態が位置 p-1 まで進んでいて、次に入れる確定トークンを x0 とする。MTP が x1..xk を出し、本体は N = k+1 トークン [x0..xk] を検証する。

- L[i] = x[i] を入れた後の logits。x[j] を受理する条件は x[j] == argmax(L[j-1])。
- 連続して受理された数を a とすると、確定するのは x0..xa の a+1 トークン。次の未確定トークンは argmax(L[a])、次の位置は p+a+1、次の MTP の入力は位置 p+a の本体の残差。
- 拒否したトークンもボーナスのトークンも、まだ状態には入れない。

## 4. 状態ごとの扱い

| 状態 | 検証中 | 確定 |
|---|---|---|
| GDN の再帰状態（36層 × 3MiB） | 書かない。トークンごとに decay、正規化した k、delta を一時領域に残す | 確定カーネルが元の状態に a+1 回の更新を同じ順で適用（遅延コミット） |
| GDN の conv 状態 | 元の状態と窓内の入力から各ブロックが自分で計算（書かない） | 受理境界の直近3入力を書く |
| PLE の n-gram 文脈と conv 状態（9 ステップ） | 確定済みの文脈と窓内のトークン・入力から計算 | 受理境界に合わせて書く |
| QSA の K/V、生のキー | 位置 p+i に直接書く（後で同じ位置に書き直されるまで読まれない） | なし |
| QSA のブロックキー | 窓内で完成するブロックは、窓内の生のキーから計算して使う | 拒否された位置のブロックは、その位置に正しいトークンが入ったときに作り直される |
| 位置 | トークン i は p+i。完成ブロック数は i ごとに floor((p+i+1)/4)（窓の末尾の値を共有しない） | p+a+1 |

N = 1 のときは、検証と確定を同じカーネルで済ませる（a = 0 が確定しているため）。

### 4.1 確定は次のステップで遅れて適用する（graph を固定したまま）

確定のための専用カーネルを別に流すと、受理数が GPU 上にしかないので、ステップごとに graph が変わるか、空振りする起動が増える。そこで「確定済みの状態 ＋ 前のステップの窓の記録 ＋ 受理数」を状態とみなし、**次のステップの各カーネルが冒頭で受理分を適用する**。

- ステップの最後に `accept` カーネルが受理数 a を決める（draft の検証。prompt と通常の decode では全部受理）。PLE の n-gram 文脈と位置を x0..xa の分だけ進め、次の未確定トークン argmax(L[a]) を `next[0]` に置き、適用すべき件数 a+1 を GPU 上に残す。
- GDN の再帰状態：検証中は状態を書かず、トークンごとの decay、正規化した k、delta を記録に残す。次のステップの `gdn_fused` は、状態を読んだあと記録の先頭 a+1 件を同じ演算で適用し、その結果を書き戻してから窓の計算に入る。状態の読み書きは今と同じ1往復で、増えるのは記録（層あたり 32 head × 8 トークン × (2D+1)）だけ。
- GDN と PLE の conv の履歴：ステップの偶奇で2面を切り替え、古い面と前の窓の入力の先頭 a+1 件から新しい面を作る。窓の入力は層ごとに残す。
- QSA：K/V と生のキーは位置に直接書くので、何もしなくてよい（拒否された位置は、正しいトークンが来たときに書き直される）。
- 1トークンずつの decode とビット単位で一致する理由：記録した値は1トークンずつのときと同じ計算列で作られ、適用も同じ演算なので、適用のタイミングが次のステップにずれるだけ。

## 5. 作業順

1. 全カーネルを N 対応にする（N = 1 で今の出力とビット単位で一致させる）。
2. 外から与えた draft で N トークンを検証して確定する経路を作る。正しい draft を与えたときに、1トークンずつの decode と logits、残差、各状態がビット単位で一致すること、拒否位置を強制した後の decode も一致することを確かめる。
3. MTP の層（QSA + MoE + GR、BF16、PLE なし）を読み込み、本体の残差（混合前の 4 本、10240 幅）と次トークンの埋め込みから draft を作る。MTP 自身の QSA キャッシュも整合させる。
4. 速度：experts を選ばれた expert の和集合で1回だけ読む、k の自動調整。

## 6. MTP 層の実装（§5 の 3）

SGLang の `qwen4_exp_mtp.py` に合わせた。

- MTP の位置 j の行は、本体の位置 j の残差 h_j（最終層のあと、最後の混合の前の 4 本）と、トークン x_{j+1} の埋め込みを組み合わせる：
  `R_i = fc_embedding(norm(embed(x_{j+1}))) + fc_hidden(norm(h_j)_i)`。norm は (1 + w) の RMSNorm で、h の方は 4 本 10240 要素をまとめて正規化する。RoPE の位置は j。
- そのあと QSA + MoE の 1 層と、MTP 自身の最後の混合を通し、本体の lm_head で x_{j+2} の draft を出す。
- 重みは `mtp.*`。experts は BF16（5 GB）なので、読み込み時に GPU で NVFP4（ModelOpt と同じ丸め）にして、本体と同じ MoE カーネルで使う。draft にしか効かないので、量子化の誤差は受理率にしか影響しない。dense は TSJ_DENSE の `mtp` で MXINT8（既定）か BF16。
- MTP 自身の QSA キャッシュを持つ。各ステップの最後（`accept` のあと）に、窓の位置 p..p+N-1 の行（`accept` が作る次トークン列 `mtp_tok` と本体の残差の行）を MTP に通してキャッシュを埋める（確定しなかった位置の行は、次のステップで同じ位置に書き直される）。
  - prompt は塊ごとに、次の塊の先頭トークン（lookahead）を渡すので、塊の境目も正確。
  - 確定した最後の行から1つ目の draft、その MTP の残差を次の入力にして残りの draft を作り、`next[1..]` に書く。
- 1回の投機ステップは、本体の検証（N = k+1）、`accept`、MTP の窓、draft k 個を1つの CUDA graph に入れ、ホストは確定したトークン（`acc_out`）だけを読む（`Engine::spec_step`）。

## 7. サンプリング（kernels/decode/sample.cu）

- temperature、top_k、top_p（transformers の TopK → TopP と同じ意味）。パラメータは GPU のメモリに置くので、変えても graph を取り直さない（`Engine::set_sampling`）。
- Gumbel-max で選ぶ。ノイズは (seed, 位置, トークン) のハッシュなので、同じ位置の抽選はどのステップ・どの窓で計算しても同じ。
- 投機では窓の各位置でサンプルし、draft がそのサンプルと等しいときだけ受理する（`accept` は貪欲と同じ）。draft d は確率 p(d) で受理され、拒否したときに残るのは「d 以外に制限した p」からのサンプルなので、決定的な draft に対する厳密な投機サンプリングになる。しかも同じ seed の 1 トークンずつのサンプリングと同じトークン列になる（縮小モデルのテストで確認）。
- 速さ：最初の実装は 1 ブロックで語彙全体（248K）を約 65 回なめていて、1 トークン約 2.4ms かかった（サンプリング時の投機なしが 140 → 105 tok/s）。top_k ≤ 64 のときは、128 ブロックで語彙を分けて各ブロックの上位 top_k を残し、それを合わせる 2 段構えにした（同点の扱いだけ、k 番目と同じ値をすべて残す transformers と違い、トークン番号で切る）。

## 8. Sol の第3回（N トークンの高速化、`reviews/20261021-0049-multitoken.md`）

取り込んだもの：
- GEMV の x を XOR で並べてバンク競合を除き、N ≥ 4 では 1 warp 1 行にする。
- `gr_up_mix` で重みの復元を全トークンで共有し、並べ替えた warp の和を使う（xor の順は同じなのでビット一致）。

## 10. 見送り：draft 用の語彙の絞り込み

MTP の draft 1 個ごとに 248K 語彙の lm_head（MXINT8 636 MB、約 0.47ms）を読んでいる。よく使う語に絞れば 1 個あたり約 0.4ms 減らせる（出力は変わらず、受理だけが下がる）。手元のコードと文書 5,100 万トークンで頻度を数えると、上位 32,768 語でコーパスの 99.98% を覆ったが、コード中心で「首都」「東京」すら入らず、チャット出力の被覆は 89% だった。一般の文章の頻度表が手に入るまで保留。代わりに draft 専用の lm_head を NVFP4 にする（半分の 0.22ms、被覆の問題なし）案がある。

## 11. Sol の第4回（窓の高速化、`reviews/20261021-0342-window-r4.md`）

Sol が出した変更は2つ。どちらも GPU なしで書かれ、速度とビット一致は未確認のまま届いた。

- **GEMV の入力の行間共有**（`gemv2.cu`、NT > 1 かつ R > 1 のときだけ）：重みを 2 要素ずつ R 行ぶん復元し、各トークンの入力 2 要素を 1 回読んで R 行すべてに使う。行・トークンごとの FMA の順は同じ。R4/P2/NT4 のレジスタが 128 → 89 になる。NT = 1 の機械語は変わらない。`TSJ_NVCC_DEFINES=-DTSJ_GEMV_ROW_REUSE=0` で外せる。
- **GDN の列分割**（`gdn_window` + `gdn_window_norm`、N > 1 のとき）：value の 32 列ごとに CTA を分け（48 → 192 CTA）、次トークンの k·S を今のトークンの出力の内積と重ね、正規化は窓の全トークンを並列に後でやる。遅延コミットの記録と演算はそのまま。

### 不具合：同じ式でもカーネルが違うと丸めが変わった

`gdn_window` は最初、記録の k が `gdn_fused` と最後のビットで食い違った（新しい `tests/gdn_window.rs` で検出、tiny_e2e と tiny_verify も不一致）。conv の `w.x h0 + w.y h1 + w.z h2 + w.w x` を、コンパイラが `gdn_fused` では fma(w.y, h1, w.x h0)、`gdn_window` では fma(w.x, h0, w.y h1) と、違う掛け算を FMA に取り込んでいた（PTX で確認）。`gdn_fused` の順を `conv4` に明示して両方で使う（`gdn_fused` の PTX は mul が mul.rn になるだけ）。二つのカーネルが同じビットを出す必要がある式は、積が二つ以上なら fmaf で順を固定する。

直したあと、`gdn_window`（D 32/64/128、受理数 0〜8、PDL の有無で出力・状態・conv・記録が一致）、tiny_e2e（N = 2, 3, 4, 5, 8）、tiny_verify、mxfp8 はすべて通り、実モデルのロジット（ja、code）は前回とバイト単位で同じ。

| 同上 ＋ 文脈（プロンプトと出力済み）に出た語 | 92.8% | 95.6% | 97.0% |

中国語の出力は 65,536 語でも 74〜84% しか覆えない。手元に一般の多言語コーパスがない限り、受理が目に見えて落ちるので見送った。

### NVFP4 のコピーと、上位候補の採点し直し

- 読み込み時に lm_head（bf16）を GPU で NVFP4 にしたコピーを draft 専用に持つ（MTP の experts と同じ丸め、357 MB 増える）。MXINT8 の 655 MB に対して 1 回に読むバイトが 55%。
- `draft_head`（gemv2.cu）：16 レーンで 1 行、1 warp 2 行 × 2 組、重みの読み込みはすべて griddepcontrol.wait の前。argmax を畳み込み、ブロックごとの最良（値、行）だけを書く（logits を書かない）。
- `draft_pick`：NVFP4 の上位 4 候補を、本来の lm_head（MXINT8）の行で採点し直して選ぶ。NVFP4 だけだと日本語の受理が 2% 落ちた（k = 3 で 2.30 → 2.25 トークン/ステップ）が、採点し直すと 6 本すべてで MXINT8 と同じ受理になった。
- MTP の head（3 回、profile）：1.31ms → 0.84ms。
- `TSJ_DRAFT_HEAD=int8` で元に戻る（コピーを作らない）。`TSJ_DRAFT_RG=4` は 1 warp 2 行 × 4 組（差はばらつきの内）。

### draft 数の自動調整を深さごとの受理率に

draft の 1 ステップの費用を測り直した（k = 0〜5、4 本の平均、ms）：7.03、9.90、12.86、14.61、17.82、19.53。`spec_cost` を [1.12, 1.58, 2.05, 2.33, 2.84, 3.11] にすると、§9 の「全 draft で同じ受理率」の見積もりは深い draft を買いかぶり、自動が k = 3 固定より遅くなった（6 本の平均で k = 3 の 1.007 倍）。MTP は連鎖するほど外れやすいので、深さ j ごとに「j − 1 個目まで受理されたときに j 個目が受理される率」a_j を数え（減衰 0.97、a_{j−1} に縮める）、確定数の期待値を 1 + a_1 + a_1 a_2 + … にした。k = 3 固定に対して 1.021 倍（ja 1.073、travel 1.065、code 1.020、lru 1.008、en 0.992、zh 0.967）。

- N = 3 は N = 4 とほぼ同じ費用（どちらも 4 トークン用にコンパイルしたカーネル）、N = 5 は N = 4 より 2.6ms 重い（8 トークン用）。k = 2 と k = 4 が選ばれにくいのはこのため。

## 13. API セッション向けのエンジン側の変更（2026-10-21）

- **`tsumuji_engine::open(dir, 0, …)`：文脈長を空き VRAM から決める。** 重みを読んだあと、1,024 トークン分の状態を試しに確保して文脈に依存しない部分を測り、残り（2 GiB を空けておく）に入る最長の文脈を 256 単位で選ぶ。上限は `max_position_embeddings`（`Dims::max_pos`、262,144）。選んだ値は `Engine::ctx`。文脈に比例するのは QSA 12 層と MTP の K/V・生のキー・ブロックキー（1 トークン約 61.6 KB、262,144 トークンで 16 GB）。実機では上限の 262,144 になった。`tsumuji run --ctx 0` で確認できる。
- **スナップショットの使い回し。** `save_state` は、捨てられた `Snapshot` のバッファ（最大 4 組、1 組約 175 MB）を使い回す（`Snapshot` を drop するとエンジンに戻る）。`save_state_into(&mut Snapshot)` は既存のスナップショットにその場で上書きする（`Snapshot::default()` から始めると初回だけ確保）。`Snapshot::bytes()`、`trim_snapshot_pool()` もある。従来の `save_state` / `restore_state` はそのまま使える。tiny_verify に、上書きと使い回しのどちらから戻しても続きがビット単位で同じになるテストを足した。
